# Seguridad y privacidad reales: red, DNS y controles locales

Revisión acotada del repositorio y observaciones locales read-only del 22-11-2026. No es una auditoría exhaustiva ni una certificación de ausencia de vulnerabilidades. Se separan **declarado**, **observado** e **inferencia**. No se leyeron secretos, perfiles privados de navegador ni configuraciones generadas dentro de `/nix/store`; no se ejecutaron builds, rebuilds, escaneos, pruebas de fuga ni modificaciones de red. Se omitieron identificadores personales, direcciones del usuario y nombres de redes privadas. `flake.lock` ya estaba modificado al inicio y no se tocó.

## 1. ¿Qué protección DNS está declarada y qué queda realmente comprobado?

### Takeaway

El repositorio declara **DNSCrypt con relays de anonimización**, no DNS-over-TLS. Hay dos matices importantes: la selección explícita de servidores hace que los filtros `require_*` no sean una garantía efectiva adicional; y el modo de emergencia es una degradación deliberada a DNS sin cifrar. La observación local confirma servicio activo y resolución del sistema apuntando a loopback, pero no demuestra por sí sola el cifrado de cada consulta ni qué proveedor atendió cada petición.

### Cited Findings

- **D1 — Punto fuerte, declarado:** NetworkManager deja de administrar DNS; el sistema apunta a loopback IPv4 e IPv6 y el proxy escucha solamente en esos loopbacks. Se habilitan DNSCrypt y relays, y se deshabilita DoH dentro de este proxy. No confundir este transporte con TLS: DNSCrypt es otro protocolo. [Configuración: `modules/core/dns.nix:90-102,133-135,166-182`](../../modules/core/dns.nix#L90); [documentación del proyecto](https://github.com/DNSCrypt/dnscrypt-proxy/wiki/Anonymized-DNS).
- **D2 — Prioridad media, garantía sobreestimable:** hay una lista explícita `server_names` y a la vez `require_dnssec = true` / `require_nolog = true`. La documentación upstream advierte que, con servidores nombrados explícitamente, se respeta esa elección **independientemente de los filtros**. Por tanto, no debe decirse que estas banderas obligan en ejecución a usar exclusivamente operadores sin registros o con validación DNSSEC. Tampoco demuestra que los seleccionados incumplan: habría que comprobar sus propiedades actuales. [Configuración: `modules/core/dns.nix:115-127`](../../modules/core/dns.nix#L115); [reglas oficiales de selección](https://github.com/DNSCrypt/dnscrypt-proxy/wiki/Configuration-Sources).
- **D3 — Separar tres conceptos:** cifrar el transporte reduce observación/manipulación de consultas en el trayecto; DNSSEC valida autenticidad/integridad de datos DNS firmados, no oculta los nombres; «no logs» es una declaración/política del operador, no una propiedad que el cliente pueda verificar criptográficamente. Aquí no se declaró un validador DNSSEC local independiente. Los filtros upstream describen soporte DNSSEC y ausencia de registros declarada, no una auditoría del proveedor. [Configuración: `modules/core/dns.nix:96-135`](../../modules/core/dns.nix#L96); [filtros upstream](https://github.com/DNSCrypt/dnscrypt-proxy/wiki/Configuration-Sources); [notas DNSSEC upstream](https://github.com/DNSCrypt/dnscrypt-proxy/wiki/Windows-DNSSEC).
- **D4 — Punto fuerte con límite de confianza:** las rutas de relays separan deliberadamente operadores de relay y de resolución; `skip_incompatible = true` descarta resolvers incompatibles en vez de usarlos directamente. El relay recibe la IP de origen pero no debería poder descifrar la consulta; el resolver recibe la consulta y la IP del relay. Esto no anonimiza el tráfico web ni elimina riesgos de cooperación/correlación entre partes. Las listas tienen verificación minisign declarada: autenticar una lista no certifica el comportamiento de sus operadores. [Configuración: `modules/core/dns.nix:160-203`](../../modules/core/dns.nix#L160); [modelo de anonimización upstream](https://github.com/DNSCrypt/dnscrypt-proxy/wiki/Anonymized-DNS).
- **D5 — Prioridad media de privacidad, fallback explícito:** `dns-emergencia` detiene el proxy, marca el modo y escribe como DNS el gateway disponible y un resolver público. El propio comando avisa «sin cifrar». El dispatcher conserva ese modo al cambiar de red; `dns-normal` o un reinicio permiten volver al modo habitual. No es un fallback silencioso automático declarado por el proxy. Mitigación: mantener esa vía de recuperación, pero hacer visible su estado y minimizar el tiempo en ella. [Configuración: `modules/core/dns.nix:8-11,35-67,238-251`](../../modules/core/dns.nix#L35).
- **D6 — Excepción limitada, no fuga general demostrada:** se declaran resolvers bootstrap convencionales por puerto 53 y un sondeo de conectividad al mismo puerto. Bootstrap puede resolver nombres necesarios para iniciar/actualizar las listas y no equivale a un resolver alternativo permanente para todas las consultas normales. No se capturó tráfico para establecer si se usó en esta sesión. [Configuración: `modules/core/dns.nix:144-158`](../../modules/core/dns.nix#L144); [carga de configuración upstream](https://github.com/DNSCrypt/dnscrypt-proxy/blob/master/dnscrypt-proxy/config_loader.go).
- **D7 — IPv6 no implica fuga:** `ipv6_servers = false` selecciona transporte upstream IPv4; el servicio sí atiende clientes por loopback IPv6. Esta opción no deshabilita IPv6 del sistema ni las respuestas AAAA. No se encontró una política declarada que obligue a todas las aplicaciones a usar el proxy: no puede concluirse ni «hay fuga IPv6» ni «ninguna aplicación puede eludirlo». [Configuración: `modules/core/dns.nix:91-102,133-135`](../../modules/core/dns.nix#L91); [significado de filtros IPv4/IPv6](https://github.com/DNSCrypt/dnscrypt-proxy/wiki/Configuration-Sources).
- **D8 — Navegador: límite, no hallazgo de fuga:** se instalan Brave Origin y Mullvad Browser, pero en los archivos de configuración buscados no aparecieron políticas DoH/TRR. Un navegador puede usar DNS propio y saltarse el resolvedor del sistema; esto no prueba que estos perfiles concretos lo hagan. No se abrieron perfiles, historial ni preferencias privadas. [Paquetes: `modules/home/packages.nix:25-27`](../../modules/home/packages.nix#L25); [documentación Arch sobre DNS a nivel de aplicación](https://wiki.archlinux.org/title/Domain_name_resolution#Application-level_DNS).
- **D9 — Protección antimalware no uniforme:** se balancean varios proveedores, no solo el que filtra dominios maliciosos. El propio código documenta que esto busca disponibilidad y hace que ese filtrado no sea consistente. Es una decisión de política, no una vulnerabilidad por sí misma. [Configuración y advertencia: `modules/core/dns.nix:104-139`](../../modules/core/dns.nix#L104).

**Registro de observación local read-only, sin direcciones ni identificadores privados:**

- `systemctl show dnscrypt-proxy.service` devolvió `ActiveState=active`, `SubState=running`, `DynamicUser=yes`, `PrivateTmp=yes`, `ProtectHome=yes`, `ProtectSystem=strict` y `NoNewPrivileges=yes`.
- La lectura limitada de `/etc/resolv.conf`, clasificada sin imprimir direcciones no locales, encontró únicamente los dos loopbacks estándar. No existía la marca de emergencia.
- `ss -H -lntu` más clasificación local de interfaces confirmó listeners DNS TCP/UDP de loopback y otro listener DNS sobre una interfaz de tipo puente. No se imprimieron sus direcciones. Esto es compatible con la virtualización declarada, pero no identifica por sí solo al proceso responsable.
- No se ejecutaron consultas de diagnóstico contra resolvers ni sitios de «DNS leak test».

### Inferences

- **No se ha demostrado una fuga DNS activa.** El encaminamiento local observado concuerda con la intención declarada; demostrar cifrado, validación DNSSEC y el relay realmente usado requiere evidencia adicional distinta del mero estado activo del servicio.
- **Mitigación portable, sin cambiar de distribución:** revisar periódicamente las propiedades de los servidores explícitos, o replantear selección/filtros según el modelo deseado; decidir proveedores y retención aceptables; mantener coherencia entre DNS de sistema y navegador; separar visualmente modo normal y de emergencia. No es necesario deshabilitar IPv6 de forma genérica.
- Cifrado y relays reducen quién ve qué; no hacen que el proveedor deje de ser una parte de confianza para las respuestas y las políticas que declara.

### Gaps

- No se comprobó la configuración generada actualmente cargada por el daemon ni se comparó con el árbol de trabajo; servicio activo y sockets no prueban identidad exacta entre ambos.
- No se midieron DNSSEC, correlación de relays, bloqueo antimalware, latencia, consultas de bootstrap, DoH del navegador ni egress real por IPv4/IPv6.
- No se verificaron de manera independiente las políticas actuales de retención de todos los proveedores.

## 2. ¿Qué hallazgos de seguridad son demostrables y con qué gravedad?

### Takeaway

La base tiene protecciones útiles: firewall declarado y activo, SSH no observado activo, cifrado de datos declarado, VMs sin QEMU root y aislamiento de servicio DNS. La prioridad más concreta es una excepción explícita para un runtime Electron fuera de soporte; otras mejoras dependen de amenazas concretas —red pública, invitado hostil o acceso físico— y no deben venderse como vulnerabilidades explotables ya demostradas.

### Cited Findings

- **S1 — Prioridad media/alta de mantenimiento; riesgo condicionado al uso:** Obsidian se fuerza a Electron 42 y se vacía `meta.knownVulnerabilities`, suprimiendo esa marca de seguridad del paquete. El calendario oficial da EOL a Electron 42 el **20-10-2026**, anterior a esta revisión; la política general soporta los tres majors estables más recientes. Esto demuestra una excepción consciente a la barrera de mantenimiento, **no una CVE concreta ni que la aplicación instalada esté siendo explotada**. Mitigación prioritaria: resolver compatibilidad con runtime soportado o utilizar temporalmente otra opción; no mantener indefinidamente la supresión de metadatos. La exposición aumenta con contenido o plugins no confiables. [Código: `modules/home/packages.nix:32-43`](../../modules/home/packages.nix#L32); [calendario oficial Electron](https://releases.electronjs.org/schedule); [política oficial](https://www.electronjs.org/docs/latest/tutorial/electron-timelines).
- **S2 — Prioridad media si existen invitados no confiables:** el firewall confía en toda la interfaz del puente de VMs, en vez de abrir únicamente DHCP/DNS. Esto amplía el acceso de los invitados a servicios del host que escuchen en esa interfaz o en todas ellas; no expone por sí solo esos servicios a Internet ni demuestra explotación. Mitigación: reglas específicas para servicios necesarios y mantener cerradas las interfaces físicas. La VM no debe considerarse un segmento hostil aislado solo porque use NAT. [Código: `modules/features/virtualization/default.nix:78-80`](../../modules/features/virtualization/default.nix#L78); [ejemplos oficiales de confianza de interfaz y reglas por interfaz](https://nixos.org/manual/nixos/unstable/).
- **S3 — Prioridad baja/media según red:** LocalSend abre globalmente TCP y UDP 53317, no solo en una interfaz de confianza. Con el feature activo, esos puertos quedan permitidos también en conexiones no confiables salvo otras reglas o topología que lo impidan. En la observación puntual **no apareció listener en 53317**: permitir un puerto no prueba servicio expuesto en ese instante ni acceso desde Internet. Mitigación: restringir alcance/interfaz cuando sea práctico y no ejecutar la aplicación en redes hostiles si no hace falta. [Reglas: `modules/features/localsend.nix:4-9`](../../modules/features/localsend.nix#L4); [activación del feature: `hosts/thinkpad/default.nix:9-16`](../../hosts/thinkpad/default.nix#L9); [firewall NixOS](https://nixos.org/manual/nixos/unstable/#sec-firewall).
- **S4 — Prioridad media solo frente a acceso físico/manipulación de arranque:** raíz, home y store se declaran sobre LUKS; el swap de hibernación está dentro del volumen cifrado. `/boot` se declara aparte, en FAT, y la consulta local a `bootctl status` indicó **Secure Boot deshabilitado**. El cifrado en reposo no autentica por sí mismo la cadena de arranque ni protege una sesión abierta. Mitigación según amenaza: estudiar arranque verificado/UKI y gestión de claves con recuperación probada; no activar a ciegas ni prometer defensa absoluta contra firmware o hardware hostil. [Discos: `hosts/thinkpad/hardware-configuration.nix:16-40`](../../hosts/thinkpad/hardware-configuration.nix#L16); [hibernación: `hosts/thinkpad/default.nix:36-57`](../../hosts/thinkpad/default.nix#L36); [límites y protección de arranque](https://wiki.archlinux.org/title/Dm-crypt/Specialties#Securing_the_unencrypted_boot_partition).
- **S5 — Riesgo residual bajo/media de privacidad local:** se conserva historial de portapapeles. El módulo intenta limitarlo a 50 entradas/un día y limpiar al inicio; explica que el borrado de selección viva por una extensión no equivale a borrar el historial ya almacenado. No se leyó la base ni se comprobó la política efectiva. La mitigación de menor exposición es autorrelleno y evitar copiar secretos, o desactivar/excluir historial sensible donde sea viable. No presentar los comentarios históricos del módulo como medición nueva de esta revisión. [Diseño y política: `modules/home/clipboard-privacy.nix:7-47,51-68`](../../modules/home/clipboard-privacy.nix#L7).
- **S6 — Punto fuerte, pero no frontera universal:** QEMU se declara `runAsRoot = false`; el servicio DNS observado tiene usuario dinámico y restricciones de systemd. La membresía en grupos de administración de virtualización y los canales de carpetas/USB compartidas siguen requiriendo confianza apropiada. No se revisaron las definiciones activas de cada VM ni sus comparticiones. [Código: `modules/features/virtualization/default.nix:46-76,121-122`](../../modules/features/virtualization/default.nix#L46); [estado local](#estado-read-only).
- **S7 — Punto fuerte de superficie de red:** firewall habilitado por defecto; Steam no abre puertos de Remote Play, servidor dedicado ni transferencias de juegos. CUPS está habilitado, pero los listeners 631 observados eran loopback. No se encontró habilitación de servidor OpenSSH en los módulos buscados y servicio/socket SSH estaban inactivos en la consulta local. El agente SSH de escritorio declarado no es un servidor SSH. [Base: `modules/core/system.nix:8-12`](../../modules/core/system.nix#L8); [Steam: `modules/features/gaming/steam.nix:16-20`](../../modules/features/gaming/steam.nix#L16); [CUPS: `modules/features/printing.nix:4-24`](../../modules/features/printing.nix#L4); [agente SSH: `hosts/thinkpad/default.nix:65-66`](../../hosts/thinkpad/default.nix#L65).
- **S8 — Autorización: no se identificó un bypass declarado:** usuario en `wheel`, Polkit habilitado y función Fish llamada `sudo` que invoca `run0`; existe además acceso explícito al sudo real. Esto describe interfaces de elevación, no autenticación anulada. No se encontraron reglas NOPASSWD o `wheelNeedsPassword = false` en la búsqueda dirigida, pero no se inspeccionó toda la política activa de PAM/Polkit/sudo. [Usuario: `modules/core/user.nix:7-11`](../../modules/core/user.nix#L7); [Polkit: `modules/core/system.nix:48-49`](../../modules/core/system.nix#L48); [funciones: `modules/home/programs/fish.nix:23-32`](../../modules/home/programs/fish.nix#L23).

**Observaciones locales adicionales, sin inventario sensible:** `firewall.service`, CUPS y libvirt estaban activos; SSH y su socket estaban inactivos. `apparmor.service` estaba inactivo y el indicador de kernel AppArmor devolvió `N`. `findmnt` clasificó raíz, home y store como btrfs sobre device-mapper y boot como FAT en otro dispositivo; no se leyeron cabeceras LUKS, parámetros de claves ni firmware PKI. AppArmor deshabilitado es una capa opcional no presente, **no una vulnerabilidad concreta por sí sola**.

### Inferences

- Orden propuesto: **runtime EOL y supresión de aviso → garantías reales de DNS → alcance de confianza del puente de VMs → alcance LocalSend → retención del portapapeles → arranque verificado si el modelo incluye acceso físico**.
- Hay buenas decisiones de reducción de superficie; no hay base para afirmar «NixOS es seguro automáticamente», «esta máquina es insegura» o «Arch sería intrínsecamente menos seguro».
- `loginctl lock-sessions` se solicita al cerrar la tapa antes de programar suspensión, pero eso no demuestra que el componente gráfico de bloqueo respondiese en cada ocasión. [Solicitud declarada: `modules/desktop.nix:299-329`](../../modules/desktop.nix#L299).

### Gaps

- No se revisaron CVEs/advisories de paquetes instalados ni versiones efectivamente ejecutadas. **No se atribuye ninguna CVE al host.**
- No hubo lectura privilegiada de reglas firewall activas, prueba externa de puertos, análisis de políticas completas de autorización ni pruebas de bloqueo, hibernación o arranque.
- No se inspeccionaron perfiles de navegador, permisos de extensiones, bases de historial, secretos, archivos de usuario, imágenes de VM o sus XML activos.

## 3. ¿Qué aporta Nix a la seguridad y qué se puede conservar al migrar a Arch?

### Takeaway

Nix facilita repetibilidad y recuperación; las rutas únicas, firmas y sandbox de build no sustituyen aislamiento de aplicaciones, elección de proveedores, parches ni una política de red. Casi todos los controles concretos aquí revisados se pueden reproducir en Arch; lo que requiere diseño adicional es la experiencia de despliegue/rollback y su disciplina operativa.

### Cited Findings

- **N1 — Comprobación acotada de Nix:** `nix config show`, filtrado a opciones no sensibles, indicó `sandbox = true`, `require-sigs = true`, `trusted-users = root` y `allowed-users = *` para el cliente consultado. No se imprimieron claves ni URLs privadas. El sandbox de Nix aísla **procesos de construcción**, no convierte automáticamente Brave, Obsidian o los programas del usuario en aplicaciones sin acceso a home/red. Tampoco se verificó una ejecución de build ni toda la configuración del daemon. [Implementación/documentación de sandbox Nix](https://nix.dev/manual/nix/stable/command-ref/conf-file.html#conf-sandbox).
- **N2 — Rutas y firmas no son un antivirus:** las rutas input-addressed dependen del plan de construcción, no son una prueba universal de que el contenido sea benigno; Nix distingue estas rutas de las content-addressed y aplica reglas de confianza/firma. Tener una versión fijada o una ruta con hash no establece que esté libre de vulnerabilidades. [Explicación oficial en implementación del daemon](https://github.com/NixOS/nix/blob/master/src/libstore/daemon.cc); [configuración de firmas](https://nix.dev/manual/nix/stable/command-ref/conf-file.html#conf-require-sigs).
- **N3 — Store y privacidad:** el manual NixOS advierte que los secretos incluidos como valores/rutas Nix pueden terminar en el store legible por usuarios locales. Por eso no se abrió el contenido de configuraciones generadas allí y no se puede certificar ausencia de secretos en ellas. Este es un límite general de diseño, no un secreto encontrado en este repo. [Advertencias oficiales](https://nixos.org/manual/nixos/unstable/).
- **N4 — Fijación no significa actualización automática:** la entrada de nixpkgs sigue `nixos-unstable`, pero el repositorio ofrece funciones distintas: `update` aplica la flake existente; `upgrade` primero actualiza el lock y después aplica. En lo revisado no apareció `system.autoUpgrade` declarado. No se concluye que el sistema esté sin parches ni se deduce su edad de `system.stateVersion` o `home.stateVersion`: esas versiones de estado **no son versiones de paquetes**. [Input: `flake.nix:5`](../../flake.nix#L5); [funciones: `modules/home/programs/fish.nix:54-64`](../../modules/home/programs/fish.nix#L54); [manual NixOS sobre actualización](https://nixos.org/manual/nixos/unstable/).
- **N5 — Retención de recuperación limitada, no necesariamente errónea:** hay GC semanal con borrado de generaciones de más de siete días y límite de tres entradas de systemd-boot. Conviene que el usuario conozca esa ventana al contar con rollback; no equivale a una política de backups ni mide cuántas generaciones utilizables existen hoy. [GC: `modules/core/system.nix:39-44`](../../modules/core/system.nix#L39); [menú: `modules/core/bootloader.nix:3-7`](../../modules/core/bootloader.nix#L3).
- **A1 — Portable a Arch:** DNSCrypt/relays o un resolvedor cifrado equivalente, control de DoH del navegador, firewall de entrada por interfaz y puerto, CUPS en loopback, LUKS con swap cifrado, bloqueo de sesión, QEMU sin root y unidades systemd endurecidas son controles basados en componentes disponibles fuera de NixOS. La migración debe **recrear y verificar** su configuración: no basta con copiar dotfiles de usuario. [DNS y aplicaciones](https://wiki.archlinux.org/title/Domain_name_resolution); [firewall nftables](https://wiki.archlinux.org/title/Nftables); [cifrado](https://wiki.archlinux.org/title/Dm-crypt/Encrypting_an_entire_system); [AppArmor opcional](https://wiki.archlinux.org/title/AppArmor).
- **A2 — Mantenimiento Arch:** Arch soporta actualizaciones completas, no actualizaciones parciales de paquetes del repositorio. Snapshots y recuperación se deben diseñar y probar; no atribuir a pacman por sí solo la semántica de generaciones de NixOS. Mantener un runtime antiguo sin soporte seguiría siendo un problema en cualquiera de las dos distribuciones. [Guía oficial de mantenimiento Arch](https://wiki.archlinux.org/title/System_maintenance#Partial_upgrades_are_unsupported); [soporte Electron](https://www.electronjs.org/docs/latest/tutorial/electron-timelines).

### Inferences

- Migración de seguridad mínima: reproducir primero cifrado/hibernación/bloqueo, luego firewall/SSH/listeners, después DNS IPv4+IPv6/navegador y finalmente virtualización/comparticiones. Verificar cada control y disponer de recuperación antes de retirar la instalación anterior.
- Un rollback del sistema no debe prometer deshacer archivos de usuario, bases de datos, acciones de malware o exposición de información ya ocurrida. Reproducibilidad y recuperación son ventajas operativas, no confidencialidad retroactiva.
- No es necesario imponer AppArmor, un kernel «hardened» o VPN como respuesta universal. Evaluarlos según amenazas y compatibilidad; no calificarlos como vulnerabilidades solo porque no estén presentes.

### Gaps

- El otro investigador cubre los detalles completos de rutas únicas, atomicidad, generaciones y comparación del modelo de actualización; aquí solo se delimitan sus garantías de seguridad.
- No se evaluaron snapshots/backups actuales ni restauración de datos, y no se ejecutaron actualizaciones.
- No se revisó inventario completo ni historial Git. El único archivo creado por esta revisión es esta nota.
